## 实际输出验证补充

使用 macOS 27.3、Microsoft Edge 有界面模式和 ScreenCaptureKit 同时回录系统声音与测试窗口画面。音乐沿原生播放链路输出，未接入新的 AudioContext，未使用 forcedMediaTime，未采集麦克风。测试源为 --avsync 生成的稀疏脉冲 WAV，命中 H4 帧为绿色。

采集发现：按窗口及应用过滤会漏采浏览器声音，音轨完全为零。这些录制已判无效。后改用显示器系统音频采集，画面 sourceRect 裁剪到测试窗口，获得约 0.3 峰值的非零样本。系统级声音可能包含其他应用，测量时应保持其他应用安静。

音频脉冲从 AAC 回录波形独立检测；marker 从录屏绿色像素连通区域首次出现检测。使用解码帧的实际 PTS，未假设固定视频帧率。每个稳定区间排除起始 1 秒和末尾 0.5 秒。音频比较使用脉冲能量峰值（约处于原脉冲起点后 7.5ms），全部组采用相同定义。显示帧量化约 16.7ms，编码及系统采集也带来偏差，不能视为物理屏幕与扬声器的直接测量。

### 发现并修正的额外问题

原生媒体没有经过 AudioContext，却默认减去该 AudioContext 的输出延迟。实测关闭补偿能降低录屏中的延后量。已将原生后端默认补偿设为零，保留 WebAudio 自身补偿及显式 outms 参数。新增失败回归确认原生后端不会继承独立 AudioContext 的 32ms 延迟。

## 慢速根因续查（2026-11-15）

保音调开关对照（同一显示器回录链路）中，关闭 `preservesPitch` 后，操作后 0.5× 的 P95 为 12.0ms、0.75× 为 14.5ms，额外慢速延后消失。关闭保音调仅用于定位，未作为产品修复或验收通过。

进一步检查 [Chromium AudioRendererAlgorithm](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/filters/audio_renderer_algorithm.cc)：`RunWsolaAndFill` 用本次丢弃的输入帧数计算 effective rate，`RemoveOldInputFrames` 保留搜索区域，`search_block_center_offset_` 为搜索区间一半加重叠窗口一半减一个样本，即约 25ms 源时间（30/2 + 20/2）。[AudioRendererImpl](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/renderers/audio_renderer_impl.cc) 将该 effective rate 写入 AudioClock，并明确指出 WSOLA 的非线性与反复变速的同步问题。源码读取日期为 2026-11-14/15；algorithm blob 为 0180d4cef73a64a495cf31d85c955fda85a5b815。

由此推导并经输出对照支持：不能直接把这个输入消耗位置当作拉伸窗口中心的呈现位置。保留量是**源时间**，在 0.5× 下放大为约 50ms 真实时间，在 0.75× 下约 33.3ms；这解释了此前倍率越慢、marker 越晚的趋势。窗口内的相似性匹配仍有局部非线性，因此此修正不是逐输出采样的精确反演，也不能推广为所有浏览器的统一延迟常量。

实现只对桌面 Chromium 129+、正在播放、原生媒体、保音调且非 1× 的路径恢复约 25ms 源时间中心。只影响 marker 呈现与 SFX 非外推呈现时间；`audioNow`、实际 currentTime、seek 目标和后端锚点不加入这个修正。暂停、seek、拖动预览、未就绪和强制录制不应用；Safari、Firefox、iOS、Android 不套用此浏览器实现细节。`?wsolaclock=0` 可关闭此兼容修正，用于浏览器将来改变实现后的 A/B 排查。显式 outms 仍是另外的设备校准参数。

短回录验证：保音调仍开启，第 50 次拖动之后没有附加 pause/seek；0.5× 操作后 P95 8.5ms、0.75× 25.4ms，前后中位数差均小于 20ms。但慢速只有 4/7 个样本，不以此作为最终验收。

加长第一轮的完整性门禁发现画面在后段被其他窗口遮挡，拒绝通过。该轮可见部分不能代替完整样本，也不能将漏检视为零误差。采集器随后改为独立窗口视频流与显示器系统音频流，保留共同 host-clock PTS，经 AVAssetWriter 合流；不再录入遮挡窗口。所有下面的最终验收均需使用此新采集器重跑。

版本边界核验：输入消耗时钟由 Chromium 的 [2024-07-11 提交](https://chromium.googlesource.com/chromium/src/media/+/7a81b18ce7ae5d104bd8f40f10f26c62428c4a54%5E%21/) 引入；已另行下载官方 129.0.6668.36 源码确认 effective_playback_rate 与 20/30ms 窗口同时存在。旧版 Chromium 不应用本修正。

像素检测复核：2× 阶段同一旧爆发在 38.020s 首次出现后，38.263s 的尾部片段被短去重窗口误当成新命中。该 fixture 同 pad 最短真实间隔为 1s，因此去重窗口改为 0.8s，始终保留第一次绿色出现的 PTS，不平移或筛掉高误差配对。其他 pad 的真正下一击仍单独保留。该规则只适用于本合成测试谱面。


## 最终结果：慢速系统回录验收通过
